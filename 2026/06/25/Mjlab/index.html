Mjlab

Loner2026-06-252026-10-16

概念

架构概述

Entity被组合成一个MjSpec文件，编译后传输到Mujoco Warp进行GPU仿真。ManagerBasedRlEnv负责协调MDP；RSL-RL负责训练

  • 8种manager

    • ObservationManager
    • ActionManager
    • RewardManager
    • TerminationManager:评估停止条件，区分终端重置和超时
    • EventManager:在生命周期节点（启动、重置、间隔）触发事件项。域随机化通过事件项实现。
    • CommandManger:生成并重采样目标信号（速度目标、姿态目标）
    • CurriculumManager:根据策略表现调整训练条件
    • MetricsManager:将自定义的每步值记录为episode平均值

  • 环境生命周期

    • Build
    • Initialize
    • Reset
    • Step

Entity

  • 分类：是否固定(base type)，关节类型（articulation 具有内部关节，除了可能存在的自由关节外没有其他关节）
  • 每个实体都由一个EntityCfg描述，只有spec_fn是必须的，其它所有字段都有合理的默认值。
  • spec_fn
    • 一个返回mujoco.MjSpec的可调用对象。
  • init_state
    • 默认的root姿态、root速度和关节位置/速度
    • joint_pose和joint_vel是字典，用于将正则表达式模式映射到值，模式会按照顺序与关节名称进行匹配
    • 设置joint_pose=None以使用MJCF模型中的关键帧，而不是在此处定义值。

  • articulation

    • 执行器配置，仅当entity具有可驱动关节时才需要此字段

  • Hetergeneous worlds

    • 需要在不同的并行世界中使用不同的网格资源的场景，使用VariantEntityCfg而不是EntityCfg

  • Entity提供了find_*方法，这些方法接受正则表达式并返回匹配的元素索引和名称

  • reading runtime state（读取运行时状态）
    • EntityData
      • entity.data是奖励、观察和终止函数的主要接口。它公开运动学状态（姿态、速度、加速度）、执行器力、广义力以及导出的体坐标系量（例如投影重力），所有这些都以形状为(num_envs, ...)的 PyTorch 张量形式呈现。
    • Sensors 传感器
      • 传感器在scene中配置，不是在单个Entity上配置。传感器可以引用实体元素（例如，机器人脚上的接触传感器、连接到身体某个部位的加速度传感器），也可以独立于任何实体。
      • 在运行时传感器通过env.scene按名称访问
    • raw simulation data(原始仿真数据)
      • 对于EntityData或传感器未涵盖的任何内容，可通过env.sim.data 和env.sim.model访问低层Mujoco Warp数组，这些文件以oytorch张量的形式暴露mjData和mjModel的所有字段

Actutors

  • actutors将高级指令(位置、速度、力度)转换为驱动关节的底层力，通过EntityCfg的articulation字段配置，提供内置执行器和显式执行器

Actuators types

  • 所有actuators都共享从Actuatorsfg继承的公共字段

    • target_names_expr：与关节名称匹配的正则表达式模式元组
    • armature：折算到目标关节处的转子转动惯量
    • frictionloss：静摩擦在目标关节处被建模为一个约束条件

  • Built-in actuators

    • BuiltinPositionActuators：创建用于PD控制的<position>执行器
    • BuiltinVelocityActuators：速度控制器
    • BuiltinmotorActuators：直接扭矩控制的控制器
    • BuiltinPdActutors：原生PD控制,同时跟踪位置指令和速度指令。实现方式为成对的<position>+<velocity>执行器，总和为kp * (p_target - q) + kd * (v_target - qdot)
    • ButinDcMotorActuators：封装了Mujoco的原生直流电机元件.
    • BuiltinMuscleActuators：创建具有力-长度-速度特性的仿生肌肉动力学<muscle>执行器
  • Explicit actuators（
    • IdealPdActuator：实现理想的 PD 控制器。扭矩计算公式为： tau = Kp * pos_error + Kd * vel_error
    • DcMotorActuator：扩展IdealPdActuator，通过速度依赖的扭矩饱和来模拟直流电机的扭矩-速度曲线（反电动势效应）。实现线性扭矩-速度曲线：零速度时最大扭矩，最大速度时零扭矩。
    • LearnedMlpActuator：一种基于神经网络的执行器，它使用训练好的多层感知器（MLP）根据关节状态历史预测扭矩输出。当分析模型无法捕捉复杂的执行器动力学特性（例如延迟、非线性和摩擦效应）时，该执行器非常有用。它继承了直流电机基于速度的扭矩限制。

XML执行器

  • XML执行器封装了机器人XML文件中以定义的执行器，配置程序通过将执行器的target关节名称与target_names_expr模式进行匹配来查找现有执行器。每个关节恰好对应一个执行器

执行器延迟

  • 任何执行器配置都支持内联延迟字段，用于模拟命令延迟。在实际机器人中，板载 PD 回路以 kHz 的频率运行，并可直接访问编码器，但由于推理时间和通信总线周期，策略中的位置目标到达时间会延迟。执行器延迟可以模拟这种情况：命令目标虽然延迟，但控制律仍然能够获取最新的关节状态。
  • 与观测延迟共同构成往返过程的两个环节传感器到策略再到电机

编写执行器配置

  • 由于在每个配置中执行器参数是统一的，因此需要不同参数的关节应使用单独的执行器配置

Sensors

  • 传感器位于Entity实体数据和mjlab数据访问层次结构中的原始模拟数组之间
  • 传感器在场景级别配置，而不是在单个实体级别配置的。传感器可以引用实体元素，但也可以是完全独立于任何实体的
  • mjlab提供四种传感器类型
    • 用于原生Mujoco测量的BuiltinSensor
    • 用于结构化接触检测的ContactSensor
    • 用于GPU加速的光线投射的RayCastSensors
    • 用于RGB-D渲染的CameraSensors

BuiltinSensor

  • BuiltinSensor封装了Mujoco的原生传感器。每个传感器都通过ObjRef连接到Mujoco元素（site、joint、body等），并返回一个形状为[num_envs,dim]的torch张量
类别 可用传感器
Site accelerometer, velocimeter, gyro, force, torque, magnetometer, rangefinder
Joint jointpos, jointvel, jointlimitpos, jointlimitvel, jointlimitfrc, jointactuatorfrc
Frame framepos, framequat, framexaxis, frameyaxis, framezaxis, framelinvel, frameangvel, framelinacc, frameangacc
Other actuatorpos, actuatorvel, actuatorfrc, subtreecom, subtreelinvel, subtreeangmom, clock, e_potential, e_kinetic
  • ObjRef用于标识传感器连接到哪个Mujoco元素上，Entity字段将查找范围限定在特定实体的命名空间内，传感器名称会自动添加相应的前缀（例如，实体"robot"上的"imu_acc"变为"robot/imu_acc"）。
  • 实体XML中已定义的传感器会在场景合成过程中自动被发现，并加上实体名称前缀。无需为这些传感器创建BuiltinSensorCfg

ContactSnesot

  • 在每个物理计算步骤中，Mujoco都会生成一个扁平的、非结构化的接触对列表，涵盖整个场景。
  • 一个脚的几何体可能会同时与地面产生多个接触，并与其他实体的接触交错出现，Contactensor将这个原始列表过滤成关注的接触对，将每个元素的多次接触减少到一个固定数值，并将结果打包成整洁的批量张量。
Primary和Secondary
  • 接触关系是成对的：通常你想要知道的是“机器人的脚是否接触到了地形？”，而不仅仅是“某物是否接触了某物”。primary 定义了你要测量的元素（即脚），secondary 可选地限定了它们接触的对象（即地形）。当 secondary 为 None 时，与 primary 元素的任何接触都计入其中。
  • 每侧都通过一个 ContactMatch 进行指定。该模式用于选择 MuJoCo 元素类型（“geom”、“body”或“subtree”），而模式接受正则表达式或正则表达式元组，用于与实体内的元素名称进行匹配。

RGB-D Sensor

  • 对现有相机进行封装：MJCF模型以定义相机，通过camera_name传递其名称，传感器将使用模型中相机的位置、方向和视场角
  • 创建一个新相机：当camera_name为None（默认值）时，传感器会在场景构建期间向MjSpec添加一个新摄像机。指定pos、quat以及可选的fovy来放置相机
  • Mujoco支持两种定义相机投影的方式
    • 基于视场角（FOV）
    • 基于相机内参：为了匹配真实的相机硬件，MuJoCo 相机可以通过 sensorsize、focal（或 focalpixel）和 principal（或 principalpixel）来参数化。这些字段在 MJCF XML 中设置，并提供对内参矩阵的直接控制。当存在内参时，MuJoCo 会忽略 fovy。
  • 设置parent_body可以将新摄像机附加到特定物体上，而不是世界物体上，这样相机的pos和quat坐标相对于parent的坐标，相机会随物体一起运动
  • 数据类型
    • rgb：[B, H, W, 3] uint8，彩色图像
    • depth：[B, H, W, 1] float32，深度图像
    • segmentation：[B, H, W, 2] int32，输入分割，通道0存储对象ID，通道1存储MuJoCo对象类型。背景像素为（-1，-1）
  • 渲染设置
    • 场景中的所有摄像机传感器必须将 use_textures、use_shadows 和 enabled_geom_groups 设置为相同的值。这是底层 MuJoCo Warp 渲染系统的限制，该系统为所有摄像机使用同一个 RenderContext。如果设置不一致，在构建场景时会引发 ValueError 异常。
  • 输出:CameraSensorData是一个数据类，每种数据类型有一个字段。

Scene

  • 场景将实体、地形和传感器合并到一个单一的仿真中，SceneCfg 描述了世界的内容，而 Scene 类负责 MJCF 的组合、编译以及运行时状态管理。
  • 场景从一个根 MjSpec 开始，并将每个实体的规格以唯一的名称前缀附加到其中。一个名为 “robot” 的机器人实体，其所有内部的 MuJoCo 元素（刚体、关节、几何体、执行器、传感器）都带有 robot/ 前缀，因此 base_link 变为 robot/base_link，joint0 变为 robot/joint0，依此类推。使用前缀可以防止当多个实体共享元素名称时出现名称冲突，并为观察值和奖励项提供一致的命名空间。
  • 地形（如有）以无前缀的方式附加（其元素位于全局命名空间中）。传感器在实体之后添加，并可通过带前缀的名称引用实体元素。
  • scene.compile()将组合后的 MjSpec 转换为单个 MjModel。
  • scene.to_zip(path)将编译后的模型导出为 .zip 文件,以便在独立的 MuJoCo 查看器中进行离线查看。每个实体的初始状态关键帧都会合并到导出文件中，因此模型会以其默认姿态打开。

Terrain(地形)

  • mjlab 支持两种模式：一种是平坦地面，适用于不需要变化地形的任务；另一种是程序化地形生成器，它可以生成难度可配置的地下地形网格。
  • Flat terrain（平坦地形）：默认模式。单个地面，建模为 MuJoCo 平面几何体，不包含任何程序生成的几何体。环境以规则网格排列，间距由 SceneCfg 中的 env_spacing 控制。
  • Procedural terrain(程序化地形)：对于受地形多样性影响的任务（如运动、导航），TerrainGeneratorCfg 会组装一个矩形的子地形网格。每个地块都由一个 SubTerrainCfg 生成，该配置定义了几何形状及其随难度的缩放方式。
  • 地形类型在网格中的分布方式
    • Curriculum mode(curriculum=True),每种地形类型对应一列；生成器会使用 len(sub_terrains) 列，无论 num_cols 的值是多少。同一列中的所有地块都属于同一种地形类型，难度从第 0 行（最简单）逐渐增加到第 num_rows - 1 行（最难）。proportion 字段控制的是机器人在生成时在各列中的分布情况，而非列的数量。正是这种结构化的布局，使得课程系统能够随着机器人表现的提升，将环境逐步推进到难度更高的行。
    • Random mode(curriculum=True),每个区域都会独立采样一种按比例加权的地形类型，并从 difficulty_range 中选取一个难度值。系统会遵循 num_cols 的设置。这种方式能提供最大的多样性，但没有结构化的难度递进。
  • 每个子地形的生成函数都会接收一个difficulty值，该值会线性插值地形的可配置范围。例如， BoxPyramidStairsTerrainCfg 函数 step_height_range=(0.0, 0.2) 在难度 0 时产生平坦的地面，在难度 1 时产生 20 厘米的台阶。

The Manager Layer

  • 单个ManagerBasedRLEnvCfg数据类即可完整定义mjlab环境：物理世界、智能体与物理世界的交互接口，以及定义在上面的MDP。所有内容都位于一个扁平对象中，因此无需遍历层次结构即可检查、复制和修改环境
  • Manager所有字段，标有...的为必填字段，其他所有字段均有默认值
  • 所有Manager字典都遵循相同的模式，每个条目都将一个字符串名称映射到一个术语配置对象，该配置始终至少包含一个func字段，指向该术语的可调用对象，以及一个params字典，包含转发给可调用对象的额外关键字参数
  • 管理器在每个步骤中调用func(env,**params)（当func是一个以实例化的类时，会调用类的term(env,**params)方法），term名称是任意的，他门出现在训练日志中，仅用于标识

Observations

  • 观测定义了agent在每个步骤中感知到的信息。observation manager将各个观测项组装成policy接收的输入张量。meige观测项都会经过一个可配置的处理流程：噪声注入、裁剪、缩放、传感器延迟和历史堆叠

Observation groups

  • 每个组都是一个ObservationGroupCfg，其中包含一个terms字典，该字典将字符串名称映射到ObservationTermCfg条目。manager按照注册顺序在最后一个维度上连接term输出
  • 该字典会传递给ManagerBasedRLEnvCfg(observations=...)。observation manager在初始化时解析term函数，并在此时非配任何所需的历史或延迟缓冲区
  • enable_corruption控制整个组的噪声应用：为false时，各term的噪声配置将被忽略。使得在带噪声的actor和无噪声的critic组之间共享term定义变得简单

Progressing pipeline

  • 每个步骤、每个组的每个term都按以下顺序经过以下流程compute noise clip scale delay history
    • compute：term function 被调用，必须返回一个[num_envs, D]张量
    • noise：：如果组的enable_corruption=True且该项具有 noise 配置，则应用噪声。
    • clip：如果对term设置了clip=（lo,hi），则值将被限制在该范围内
    • scale：如果设置了scale,则输出将逐元素相乘，接受标量、元组或张量作为参数
    • delay：如果delay_max_lag > 0，则该项的输出存储在一个环形缓冲区，返回先前步骤中的值
    • history：如果history_length > 0，则过去的输出会被堆叠起来

observation history and delay

  • 观测数据支持两个时间特征：历史数据和延迟数据。历史数据将过去的帧堆叠起来，为策略提供时间上下文;延迟数据则通过返回更早时间步的观测数据来模拟传感器延迟
  • history
    • 将history_length设置为 N 会堆叠该项的 N 个最新输出。当flatten_history_dim=True（默认值）时，历史维度会被折叠到特征维度中，从而生成一个适用于多层感知机（MLP）的[num_envs, N * D]张量。当flatten_history_dim=False时，输出将保留时间维度，形式为[num_envs, N, D]，适用于循环神经网络（RNN）。
    • 环境重置时，历史缓冲区将被清空，充值后的第一次观察会填充到所有历史槽中，因此策略从零步开始就能接收到有效数据
  • delay
    • 将 delay_max_lag > 0 会启用一个环形缓冲区，该缓冲区存储过去的输出并返回上一步的输出。延迟值以整数步长从 [delay_min_lag, delay_max_lag] 中均匀采样。延迟为零时返回当前观测值；延迟为二时返回两步前的观测值。

Built-in observation functions

  • 以下函数位于mjlab.envs.mdp.observations 中（也重新导出为 mjlab.envs.mdp ）。所有函数都返回[num_envs, D]张量。
Function Description
base_line_vel 机器人底座在基座标系中的线速度
base_ang_vel 机器人底座在基座标系中的角速度
projected_gravity 投影到基准坐标系中的重力向量。提供了横滚角和俯仰角信息，但未明确表示姿态
joint_pos_rel 相对于默认位姿的关节位置
joint_vel_rel 相对与默认速度的关节速度
last_action 最新动作张量，可选择性的传入action_name来选择单个动作项
generated_commands 来自指定命令项的当前命令张量。需要params={"command_name": "<name>"}
builtin_sensor 来自指定BuiltinSensor的原始数据（MuJoCo 传感器数据切片）。需要params={“sensor_name”: “<entity>/<sensor>”}

自定义observation函数

  • 观测函数接受env作为其第一个参数，并返回一个[num_envs, D]张量，其他额外参数作为函数参数声明，并通过ObservationTermCfg（params={...}提供

Action

  • action定义了策略如何控制模拟，动作管理器在每个步骤中接收策略的输出张量，将其拆分为已经注册的动作项，并将每个切片路由到相应Entity的执行器

  • 所有action类型都共享一组从BaseActionCfg继承的基本参数

    • EntityName：标识要控制的场景实体
    • scale：在应用任何偏移量之前，乘以原始策略输出。它接受一个标量或一个将执行器名称模式映射到每个目标值的字典。这可以在映射到物理上有意义的单位时保持策略输出在归一化范围内。缩放后会添加偏移；关节动作类型还提供 use_default_offset，它会自动加载实体的默认关节位置或速度作为偏移，以便原始输出为零时产生默认姿势。
    • clip：可选择的在处理后的动作（经过缩放和偏移后）到达执行器之前进行限制。

  • Action types

Type Description
JointPositionAction 设置关节位置目标，当use_default_offset=True（默认值）时，策略输出为零即表示采用默认姿态。系统会自动减去dr.encoder_bias设定的编码器偏置，以确保随机偏移量能正确传递到控制命令中
RelativeJointPositionAction 设置相对于当前关节位置的目标关节位置
JointVelocityAction 设置关节速度目标值
JointEffortAction 直接设置关节力（扭矩），无默认偏移量
TendonLengthAction 设定肌腱长度
TendonEffortAction 设定肌腱力度
SiteEffortAction 指定位置施加力和扭矩

Task-space actions

  • DifferentialIKAction通过带阻尼的最小二乘逆运动学，将笛卡尔坐标系下的位置和姿态指令转换为关节坐标系下的位置目标。每个降采样子步都会执行一次逆运动学运算，因此末端执行器能够在各个子步之间持续跟踪目标，而不仅仅是在策略频率下进行跟踪。
    • orientation_weight == 0:3D(仅位置)
    • orientation_weight > 0, use_relative_mode = True:6D(delta position + delta axis-angle)
    • orientation_weight > 0, use_relative_mode = False:7D(absolute position + quaternion)

Multiple action terms

  • 一个环境可以注册任意数量的term.动作管理器按照注册顺序连接这些term的维度，在相应的边界处分割策略的输出张量，并独立地路由每个切片。

Rewards

  • 每个奖励项都是一个函数，每一步都返回一个针对特定环境的标量值。奖励管理器计算所有奖励项的加权和，并将其返回给训练框架。
  • 每个项通过名称注册到一个RewardTermCfg，该配置包含可调用项和权重，负权重会产生惩罚

内置奖励函数

  • 可在mjlab.envs.mdp.rewards中找到，并且在任务间共享奖励。单个任务有自己的奖励，所有奖励函数返回一个形状为[num_envs]的张量
Function Description
is_alive 对于尚未终止此步骤的环境返回 1.0。与正权重一起使用作为生存奖励
is_terminated 如果环境因非超时原因终止，返回1,使用负权重可以惩罚失败的情况
joint_torques_l2 执行器力的平方和，惩罚能耗高的动作
joint_vel_l2 关节速度平方和
action_rate_l2 当前action与前一次action之间的平方差之和，惩罚策略的快速变化
action_acc_l2 二阶动作查分平方和，用于惩罚动作信号中的高频抖动
joint_pos_limits 关节位置超出soft limits时会受到惩罚，都在限制范围内时，惩罚为0
posture（class） 指数核函数：用于测量与默认关节的偏差exp(-mean(error^2 / std^2))
electrical_power_cost(class) 执行器消耗的正机械功总和，再生功率不计入其中
flat_orientation_l2 在基坐标系中投影重力向量的 x 和 y 分量的平方和。当完全垂直时为零

按dt进行奖励缩放

  • ManagerBasedRlEnvCfg.scale_rewards_by_dt默认值为 True 。启用此选项后，奖励管理器会在累加奖励之前，将每个奖励项乘以环境步骤的持续时间。这使得片段式奖励总量与模拟频率无关：以 50 Hz 运行的任务与以 200 Hz 运行的同一任务产生的预期片段奖励相同，因为每个步骤对总奖励的贡献比例会相应减少
  • 每个term的episode奖励总额以 Episode_Reward/<term_name> 的形式记录，并始终除以该term的持续时间，从而得出一个奖励率，该奖励率在不同term长度的运行中具有可比性

terminations（终止）

  • 终止条件定义了每个episode的结束时机，每个条件都是一个函数，该函数在每一步返回每个环境的布尔张量。termination manager汇总所有条件，并将结果作为终止失败或者提前终止报告给训练框架
  • 每个term通过TerminationTermCfg按名称进行注册，设置time_out=True会将条件标记为截断而非终止失败。截断会映射到 Gym 接口中的 truncated 信号；失败会映射到 terminated.代理应该估计截断之后的未来值，但不应该估计故障之后的未来值。

内置termination函数

Function Description
time_out 当episode长度达到env.max_episode_length时返回 True。使用time_out=True注册，以便管理器将其视为截断
bad_orientation 当asset的向上轴与世界向上轴之间的夹角超过 limit_angle（弧度）时，返回 True
root_height_blow_minimum 当资产的根链接高度低于 minimum_height（米）时，返回 True
nan_detection 当物理状态中的任何位置出现 NaN 或 Inf 值时，返回 True。这是一种安全机制，用于干净地终止发散的模拟

Commands

  • commands指定策略在每个时刻应达到的目标：目标速度、参考轨迹和目标位置。命令管理器生成这些信号，以可配置的时间间隔重新采样它们，并通过观测系统将它们传递给策略。
  • commands以字典的形式注册在ManagerBasedRLEnvCfg中，该字典将字符串名称映射到CommandTermCfg实例
  • resampling_time_range字段控制命令更改的频率，每次重采样后，该项都会从给定的（min,max）秒数范围内均匀抽取一个新的计时器值。每回合重置时，命令也会无条件的进行重采样
  • generated_commands observation函数按名称读取当前命令张量，并将其传递给策略

Include command terms

  • 每个任务都有其自身针对特定目标而制定的命令项
Term Description
UniformVelocityCommand 生成从可配置范围内均匀采样的平面速度指令[v_x, v_y, omega_z]。支持静止模式（部分环境接收零速度）和航向模式（偏航角速度被一个跟踪采样航向角的比例控制器所取代）。由速度任务使用
LiftingCommand 为被操作物体生成三维目标位置。支持固定和动态难度模式。跟踪指标包括位置误差和任务成功率。用于操作任务
MotionCommand 该模块从一个预先录制的 .npz 运动片段中，以流式（逐帧）方式输出参考关节位置、速度和身体姿态。支持三种起始帧采样模式：‘start’（固定从第 0 帧开始）、‘uniform’（均匀随机采样）和‘adaptive’（自适应偏向于困难区域）。在环境重置时，机器人会从采样得到的帧进行初始化，并可选择性地施加扰动（噪声）。该机制应用于（机器人）跟踪任务中

自定义command term

  • 自定义command term是一个继承自CommandTerm的类，并于一个继承自CommandTermCfg的数据配置类配对。必须实现四个方法
    • _resample_command(env_ids)：用于对新目标采样
    • _update_command：逐步更新
    • _update_metrics：记录日志
    • 一个命令属性，用于返回当前目标张量。
  • 该配置必须实现一个 build(env) 方法，用于构建配对项实例

Events

  • Event manager会在环境生命周期的特定节点执行hook。任何需要在启动时、episode重置时或者训练期间定期运行的逻辑都会被注册为事件项
  • 都通过EventTermCfg进行配置，区别在于控制每个event触发时机的mode字段

Lifecycle modes

  • EventTermCfg中的mode字段决定了term何时触发
    • startup：环境初始化期间触发一次，所有管理器构建完成后触发，所有环境同时接收，适用于不同环境间有差异但整个训练过程中保持不变的参数
    • reset：每次重置场景时触发。状态初始化和场景级域随即初始化都属于此模式。可选的min_step_count_between_reset字段用于防止episode非常短时该项过于频繁触发，上次触发后步数不足的环境跳过该项
    • interval：以固定的时间间隔触发，频率由interval_rang_s控制，该参数为一个以秒为单位的范围，每次触发后管理器从该范围均匀采样一个新的等待时间。默认情况每个环境都有单独的计时器，设置is_global_time=True,可将所有环境同步到单个共享计时器。
    • step：适用与所有环境的每个环境步骤，旨在处理需要在每个步中都进行评估的持续效果

Built-in event functions

自定义 event term

  • event的前两个参数是env和env_ids，其他参数来自EventTermCfg.parmas,会直接修改仿真状态，并且不返回任何值，复杂时间项使用类

域随即化

Domain Randomization

Curriculum

  • curriculum管理器会根据策略表现调整训练条件。训练从较简单的问题开始，随着策略展现出应对当前条件的能力，难度会逐渐增加
  • 每次环境重置都会调用curriculum term,每个term接收环境和重置环境ID集，检查一些性能指标，并将其应用于更改环境参数

built-in curriculum functions

Function Description
terrain_levels_vel 衡量每个机器人在episode中行进距离，行进距离足够的机器人会在地形网格中提升一个难度等级
commands_vel 根据训练步数扩展速度命令的范围每个阶段都会指定一个步数阈值，以及超过该阈值时要应用的新范围
reward_curriculum 根据训练步数阈值调整奖励的权重和/或参数，取代了较旧的 reward_weight 函数，并且还支持修改奖励函数参数
termination_curriculum 根据训练步数阈值调整终止项的参数，可用于随着训练的进行逐步收紧终止条件

Reward Curriculum

  • 随着训练的进行，reward_curriculum会对奖励项的权重或关键字参数进行更改。每个阶段指定一个步数阈值和一个可选的权重或参数更新。按顺序评估各个阶段，并应用已达到阈值的每个阶段
  • 常见做法是在训练初期引入较低的惩罚项，并在策略掌握基本技能后增加惩罚项
  • 还可以更改传递给奖励函数的参数
  • 单个阶段可以同时更新权重和参数

Termination curriculum

  • termination_curriculum会在训练过程中逐步调整终止条件的参数

Metrics

  • 指标管理器会将每步的标量值记录为回合平均值，指标本身不具有权重，也不会根据步长进行缩放
  • 每个指标项都会以其名称注册到ManagerBasedRlEnvCfg的指标字典中。配置非常简单：一个可调用对象和一个可选的参数字典。

Recorders

  • recorder manager 提供生命周期hook,用于在rollcout过程中记录数据，不会影响优化循环
  • 每个recorder term都是一个需要自己实现的类，mjlab会在合适的时机调用
  • Lifecycle hooks
    • record_pre_reset(env_ids): 在终止的环境被重置之前，在 env.step() 内被调用。
      • ’obs_buf`:保存上一步结束时的观测值
      • action_manager.action:保存最终动作,随后_reset_idx会立即将该变量在这些环境中清除
      • reward_buf:记录最终奖励
    • reward_post_reset(env_ids)：在重置完成且有新的观测数据可用时调用。
    • record_post_step： 在每次 env.step() 结束时调用，并传入新的观测值。
    • close：环境关闭时调用

Writing a recorder tern

  • 继承 RecorderTerm 类，并重写所需的hook，环境变量可通过self._env获取，从而可以访问self._env.obs_buf、self._env.action_manager.action以及所有其他管理器。
  • registration

Training & Debugging

  • mjlab使用RSL-RL进行on-policy强化学习，分为三个部分
    • 任务注册：将环境和训练配置捆绑在同一个名称下
    • VecEnv wrapper：将mjlab环境适配到RSL-RL期望的接口
    • configuration dataclasses：控制训练运行

Task registry

  • mjlab中的每一个任务都是一个二元组：一个环境配置（ManagerBasedRlEnvCfg）和一个训练配置（RslRlOnPolicyRunnerCfg），task registery将字符串名称映射到这个二元组，以便可以通过CLI按名称启动训练
  • 注册需要
    • task_id：Mjlab-{Category}-{Terrain}-{Robot}
    • env_cfg：用于训练的ManagerBasedRlEnvCfg
    • play_env_cfg：一个禁用随机化并将回合长度设置为无限的变体，用于评估
    • rl_cfg：包含 PPO 超参数和网络架构的RslRlOnPolicyRunnerCfg
    • runner_cls：可选的自定义运行器类（默认为MjlabOnPolicyRunner）

Configuration

  • 包含runner设置、网络架构（RslRlModelCfg）和PPO超参数（RslRlPpoAlgorithmCfg）

检查点

  • runner会在logs/rsl_rl/{experiment_name}/目录下查找最近的一次运行目录，并加载编号最大的检查点。可通过--agent.load-run（对目录名称进行正则表达式匹配）和--agent.load-checkpoint（对检查点文件名进行正则表达式匹配）来缩小搜索范围

Viewer

  • 基于mujoco构建的原生查看器和viser

Viser

  • 侧边烂
    • Controls：播放/暂停、重置、速度调整、环境选择和显示设置
    • Rewards：实时现实每项的奖励图表，可通过复选框切换
    • Metrics：当使用MetricManager时，实时现实每项的指标图表
    • Cammera Feeds：场景中每个CameraSensor的实时 RGB 和深度图像面板。深度比例滑块可调整可视化范围，视锥切换可在 3D 场景中显示摄像机的视野
    • Groups：显示或隐藏Mujoco gemo和site组
